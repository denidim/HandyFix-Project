## 3bs. Stylesheets: One Bundled, Fingerprinted File Instead of an `@import` Chain (2026-10-01)

The fix for the stale-stylesheet problem recorded in Section 3bq, done the way Microsoft's bundling guide describes rather than as a cache-header patch (the user's call).

- **The cause**: `_Layout` linked `site.css` with `asp-append-version`, but `site.css` held only 23 `@import` lines. The version hash covered that list, not the 23 files, and those were served with no `Cache-Control`, so browsers kept them for as long as they guessed was safe. A changed `logo.css` reached nobody until their copy expired. The `/* Force recompile cache trigger v7 */` comment in `site.css` (bumped three times since July) was a manual attempt at this and could not work: it refreshed the list, not the files it points to.
- **WebOptimizer finished.** The package was installed long ago and left half set up: its bundle was fed `site.css` (so it still contained the 23 imports), no page linked it, and its tag helper was off. Now `AddCssBundle` gets the real files, both layouts link `/css/site.min.css`, and WebOptimizer's `LinkTagHelper` adds `?v=` with a hash of the combined content. A change in any source file changes the address.
- **`SiteStylesheets.cs`** holds the ordered list (the cascade order `site.css` used to define). `fonts.css` (new) carries the two Google Fonts `@import`s and is first, because an `@import` only works at the top of a file; `icons.css` (new) carries the two Material Symbols rules that sat at the bottom of `site.css` and is last, so their place in the cascade is unchanged. `site.css` is deleted. So is `wwwroot/css/site.min.css`, a 680-byte leftover from the project template that sat on the bundle's address.
- **Per environment, set in `Program.cs`** rather than left to the package's defaults. Live (anything but Development): one combined, minified file, served with `Cache-Control: max-age=31536000,immutable`. Development: each source file linked by itself with its own `?v=`, in the same order, which is Microsoft's stated practice and keeps file names visible in the browser's tools. Disk cache off everywhere, so nothing is written next to the app in the container.
- **Two quirks of WebOptimizer 3.0.477, both found by testing**: (1) `@addTagHelper *, WebOptimizer.Core` also registers its copies of the built-in link and script helpers, which then run twice (every `asp-append-version` link came out with `?v=…&v=…` and a second `href`); only `WebOptimizer.Taghelpers.LinkTagHelper` is registered. (2) In Development it writes each link exactly as the source path was given, so `css/fonts.css` became a relative link that breaks on any page not at the site root; the paths in `SiteStylesheets.cs` start with `/`.
- **Not touched**: `pages/admin.css` (one file, already versioned by `asp-append-version`); the JavaScript (`site.js` is one file, already versioned; the old `/js/site.min.js` bundle registration is still there and still unused). *That registration was removed in Section 3df.*
- **Size**: the combined file is 103 KB against 142 KB for the sources, in 1 request instead of 24.
- **For browsers that already hold old copies**: they keep them until their guessed lifetime runs out, so the first visit after this deploy may need one hard refresh. After that the problem cannot recur.
- **Noticed, not changed**: the staging Caddyfile has no `encode` line, so CSS, JS and HTML go out uncompressed. `Home/Index.cshtml` hides every `<section>` and fades it in on scroll from a script (inline then, `wwwroot/js/home.js` since Section 3dj), which is what makes full-page screenshots of the home page unreliable unless they wait for it. `.final-cta {}` in the CSS is an empty rule.

### Verified

- **Every page, before and after**: 160 full-page screenshots (68 public pages at 1440px and 390px, 4 pages as print, 10 admin pages at both widths, signed in) taken before the change and compared pixel by pixel. Two identical "before" runs differ on 7 of 160 by at most 0.01% (apart from the home page's fade-in), which is the noise floor. Live mode: 154 identical, the other 6 within that noise. Development mode: the same, after re-shooting 8 phone pages that showed a 1px text shift once (three re-shoots, all byte-identical to "before").
- **The minified file against its sources**, rule by rule as Chrome parses both: 972 rules against 971. The one missing is the empty `.final-cta {}`. Every other difference is notation (`#ffffff` as `#fff`, `border: none` as `border:0`, `outline: none` as `outline:0`, spacing, the `?v=` WebOptimizer adds to two image URLs).
- **The fix itself**, with the app running in live mode: appending a rule to `logo.css` changed the link from `site.min.css?v=4E018…` to `?v=I-met…` with no restart and the combined file contained the rule; undoing the edit brought the first hash back. A repeat request with the file's `ETag` gets `304`.

## 3bv. Values in Script Blocks Written as JSON, Not as HTML (2026-10-07)

Found while the phone number was going into the structured data (Section 3bu), raised by the user from a review of that change, and fixed the same day at the user's request.

- **The cause**: Razor HTML-encodes every value it writes. That is right in HTML text and in attributes, where the browser decodes it again. Inside a `<script>` block nothing decodes it, so whatever reads the block gets the entity itself.
- **What it did to the structured data**: a service name went out as `Radiator &amp; TRV Replacement` (12 services and 2 areas have `&` in their name), and the pound sign in the FAQ answer as `&#xA3;90.00` on every bookable service page, 28 of them. The blocks were still valid JSON, so nothing reported an error; search engines simply read the wrong text.
- **What it did on the booking page**: `/Booking?date=...` wrote the date from the link into the page's script, inside single quotes. HTML encoding stopped quotes and tags, so no link could run code of its own (tried: a quote, a double quote and a closing `</script>` tag all came out as harmless entities). It left a backslash alone, and `date=\` swallowed the closing quote: a syntax error that stopped the whole booking script for whoever opened that link.
- **The fix**: every value written inside a script block goes through `Json.Serialize`, which writes a quoted, escaped JSON string (`&` as `&`, `<` as `<`, `\` as `\\`) that a JSON reader and a script engine both turn back into the original text. Changed: in `Services/Details.cshtml` the service name (three places), the price and the image path; in `Areas/Details.cshtml` the area name (twice) and the three breadcrumb addresses; in `Booking/Index.cshtml` the chosen service id and the date.
- **The JSON-LD price is formatted with the invariant culture**, so it is `90.00` on any server. It followed the server's regional settings before, which could have written `90,00`.

## 3bw. Booking Link: The Date Is Read by the Model Binder (2026-10-07)

The item Section 3bv left open, fixed at the user's request, the way the rest of the project already handles dates.

- **The problem**: `BookingController.Index` took `date` as text and passed it to the page as it came. After Section 3bv a value like `abc` could no longer break the script, but the calendar still opened on "undefined NaN" with "Error loading slots".

ASP.NET Core's model binder parses the value from the link before the action runs; text that is not a date leaves the parameter `null`, and the page opens on today. Parsing the text by hand in the controller would have been a third way of doing one job. The binder also reads link values with the invariant culture, so the result does not depend on the server's regional settings.
- **A link with a time in it** (`2026-10-20T15:30:00`) is a date too; the page uses the day.
- **Not changed**: `GetSlots(string date)` and `HomeController.Contact(string date)` still parse their date text by hand. Both work, and `GetSlots` has tests written around that shape (`GetSlotsShouldRejectUnparseableDates`), so they were left alone. ## 3cb. Launch Sprint L3: Abuse Protection, Validation and Notifications; Nineteen Faults Found on the Way (2026-10-08)

**What a submission to a public form now goes through, in order**: the rate limit, the antiforgery token, the form's own rules, the hidden box and the time check, Turnstile, then for an enquiry the duplicate check and for a booking the postcode check, then the photos, the save, and last the emails. ### What was built

- **Seeders fill an empty table and leave the data to the admin (item 9).** The item asked for the services seeder to stop overwriting an admin's price. Reading the code showed two worse faults, both proven by a test before anything was changed: deleting a seeded service in the admin panel made the next start fail on the unique index on `Slug` (the seeder looked the service up by name, could not see the soft-deleted row, and inserted it again), and renaming one brought the old one back as a 38th service. A seeder cannot tell a renamed service from a missing one, so no rule based on `ModifiedOn` or a flag cures it. `ServicesSeeder` and `ServiceAreasSeeder` now insert only when their table holds nothing at all, deleted rows counted, in one save so a start that fails part-way cannot leave a part-filled table. `TechniciansSeeder` counts deleted rows too. The cost: a change to the seeder's list no longer reaches a database that already has services. It goes in through the admin panel, or a migration.
- **"Delete Permanent" on an enquiry is a real delete (item 8).** `InquiriesService.DeleteAsync` removes the photos from Cloudflare R2, then the photo rows and the enquiry in one save. The photos go first: if storage cannot be reached nothing is removed and the admin returns to the enquiry with a message, where the other order could leave photos nothing points at. `CloudflareR2Service.GetObjectKey` works the object out from the saved address.
- **Stricter rules on the three forms (item 4).** `PersonName`, `StrictEmail`, `UkPhone` and `UkPostcode` in `HandyFix.Web.ViewModels/Validation/`. Each is a `RegularExpressionAttribute`, which ASP.NET Core writes into the page as a pattern, so the browser shows the message as the visitor types with no script of ours. A pattern therefore has to mean the same in .NET and in JavaScript: no named groups, `[0-9]` for `\d`. `NotMostlyLinks` (server only) refuses a message with more than three links or with nothing much left once they are taken out. The booking description needs 20 characters.
- **Postcode districts on service areas, and the booking check against them (item 4).** The item said "checked against the served areas", and the areas held no postcodes. `ServiceArea.PostcodeDistricts` (migration `AddPostcodeDistrictsToServiceArea`, which also gives the 15 seeded areas their lists) is editable on the admin area form and shown in the admin list. With no district on any area the check is off, so an empty setup cannot turn every booking away. The booking keeps one address: street, then the postcode written the standard way.
- **A form sent twice is sent once (item 5).** `site.js` marks any POST form when it is sent and stops further submits of it until the next page arrives, with a spinner on its button; this covers the admin panel too. On the server the same email with the same message inside ten minutes is the first enquiry again: thanked, not saved, photos not uploaded twice.
- **Enquiries and applications email the company and are acknowledged (item 6).** The notice goes to `Admin:NotificationEmail` with the sender as Reply-To, so pressing Reply answers the customer. The acknowledgement repeats nothing the sender typed, not even their name: anyone can type any address into a public form, and an email that echoed the form back would let a program use the site to send a stranger its text from the business's own domain.
- **The hidden box and the time check (item 1).** `FormGuard` and the `_FormGuard` partial: a text box moved off the page and out of the Tab order, and a signed stamp of when the form was shown. Filled in, unsigned, or back in under three seconds means a program. Contact and Join Our Team answer with their usual thank-you and save nothing. A form shown again after an error keeps its first stamp, or a person's quick correction would be dropped in silence.
- **The rate limit, and the site's own pages for error statuses (item 2).** ASP.NET Core's limiter: ten form posts in ten minutes between the three forms, sixty slot lookups a minute, both settable. A visitor is an address; an IPv6 address counts by its first half. The 429 needed a page, and one mechanism gave the site its missing 404 page too: a response that ends in an error status with nothing in it is shown as the site's own page for that status, for a request that asked for a page. `ErrorsController` takes no services, so it can show itself when what broke is something the rest of the site needs.
- **Cloudflare Turnstile (item 3).** `TurnstileVerifier` asks Cloudflare about the token and passes it only if it was earned on this form and this site. A failure is said out loud, with the phone number, because a person can fail it. If Cloudflare cannot be reached in five seconds the submission is let through and the failure logged: refusing every enquiry and booking during an outage would cost more than what the other checks let through. With no keys the check is off in Development and the form pages fail everywhere else, the third use of the "fail loud outside Development" pattern. The widget takes its compact shape where a form is narrower than 300px. The Privacy and Cookie policies say the forms carry the check.

## 3cc. Email on Role Addresses; the Admin Account Changed and Recovered Without a Developer; Four Faults Found on the Way (2026-10-08)

Two pieces of Launch Sprint L4, done together because the second leans on the first: the staging half of item 3 (Brevo), and all the code of item 12 (the admin account). `docs/WORKFLOW_EMAIL.md` and `docs/WORKFLOW_ADMIN_ACCOUNT.md` are new and are the references; this section records what was built, why it was built that way, and what turned up.

### Email: no person's address in any setting

**What was wrong.** Staging's three email settings held the developer's own address: both "from" addresses and the address notices go to. Every test email staging sent to a "customer" came from a private person, and `.env.example` told the next developer to do the same.

- **The rule, written into `docs/WORKFLOW_EMAIL.md`: role addresses only.** Every address the site sends from or to is a role address on the business's domain, and who reads one is a single forwarding rule in Cloudflare Email Routing. When a person changes, one rule changes and no server, key or document does. It is the lesson of Section 3bt (accounts must not hang off one person) applied to settings.
- **Staging sends from `bookings@`**, as the live site will: both "from" settings are empty there now, which means the default in `EmailSettings`. Brevo refuses a sender it has not verified and the domain's signing records only prove themselves on a real send, so staging now finds a fault in either before launch depends on them.
- **Staging's notices go to a developer role address** on the domain, which forwards to whoever tests staging. Its name is in the private infrastructure doc only: written in a public repository it would collect junk mail.
- **Staging marks its subjects `[STAGING]`.** Sent from the same address, a test email otherwise reads exactly like a real one. `SubjectPrefixEmailSender` wraps the Brevo sender when `Email:SubjectPrefix` holds anything; the live site leaves it empty. A wrapper, not a change to the six places that send: a seventh email cannot forget the mark.
- **One Brevo key per environment**, both from the company's account. Staging runs on a new one, moved to the server without being shown (a one-line file in the untracked `docs/private/`, piped over SSH into `.env`, then deleted). The key before it was in the same account; it had been written in a private doc since August, and replacing it cost nothing. It was deleted in Brevo the same day, once the new one had sent real emails.

### The admin account

**What was wrong**, as L4 item 12 found on 2026-10-01: the password could only be changed by a developer, "Forgot password?" sent nothing, and the login was an address on a domain the business does not own, written in a public repository.

- **An Account page in the admin panel** (`/Administration/Account`, in the sidebar): change password, change login email, sign out. The email change asks for the current password again, so a panel left open is not enough to move the login, and with it the password reset, to somebody else's mailbox. No confirmation email: the password is the proof. `AdminAccountService` does the work and the controller only places each refusal under the box it is about.
- **"Forgot password?" works.** The site's own two pages, in its own look, sending through the site's own sender. Until now the link opened the Identity UI package's page, which told the owner to check an inbox and sent its email through a sender that sends nothing. Made to work and not removed, because an owner who forgets his password would otherwise be locked out until a developer steps in, which is the "he will not maintain code" principle (vision doc Section 1). The form carries the same guard as the customer forms. The answer is the same whether or not the address is a login. The link works for two hours and once.
- **The login email is a setting**, `Admin:SeedEmail`, beside `Admin:SeedPassword`. The seeder now asks "is there an administrator?" and not "is there a user with this address?". Two reasons: the real login is no longer in a public repository, and once the login can be changed in the panel the old question would have made a second administrator, with the seed password, at the next start.
- **Both settings are read once in a database's life**, at the start that finds no administrator. This was already true of the password and nothing said so; the README, the deployment doc, `.env.example` and the compose file now all do.
- **Only six pages of the Identity area have a route.** The Identity UI package brings about thirty in its stock look, and a signed-in admin could open all of them: "delete my account", two-step sign-in setup, an email change that waits for a confirmation nobody is sent. `IdentityPages` lists what is open, not what is closed, so a page a later version of the package adds starts closed.
- **Guessing the password is limited.** The login counted no wrong passwords and had no rate limit, with a six-character minimum. Now: five wrong in a row pause the account's login for five minutes; signing in and resetting share an allowance of ten sends in ten minutes per address, apart from the customer forms'; the minimum is ten characters, and length is the only rule. The pause is per account and the allowance per address: one stops many computers guessing slowly, the other one computer guessing fast.
- **One message for every failed sign-in**, naming the rule: "That email and password did not match. After 5 wrong tries in a row the login pauses for 5 minutes." The same for a wrong password, for an address that is not a login and for a paused login, so the page tells a stranger nothing and tells the owner what he may have run into.
- **A reset ends a pause.** Forgetting the password is the usual reason for five wrong tries, so the reset link has to be the way out and not a second wait.

## 3ce. The Job Book: Every Job Has a Page, Booked on the Website or Written In by the Admin; Thirteen Faults Fixed on the Way (2026-10-09)

The business said, on 2026-10-08, that the website has to be the one place where all of its work is kept: a job booked on the website and a job taken by phone alike. Until now the site knew only the first kind, and its admin pages had been built for a flow nobody had walked through end to end. This section is the build of what was agreed that day, in five steps, pushed together. `docs/WORKFLOW_BOOKINGS.md` is the reference for how it works; this section records what changed and why.

### What was agreed (2026-10-08, by the business, one question at a time)

- **Every job gets a page**, however it arrived: the website, phone, WhatsApp, an enquiry, an agency. The page says where it came from, so each month shows where the work comes from.
- **A job written in by the admin needs a name and a phone number.** The site sends no email for it, and its time is not promised. *(Changed 2026-11-08, Section 3dt: its customer is emailed once a technician is picked.)*
- **Slots and the calendar stay as they are.** A slot is a start time and one hour is the least a customer pays for. The admin blocks further hours by hand; blocking by a job's length, and a "block the next hours" button, were both turned down.
- **A deposit is only paid on the website, and only a deposit promises the time.** A phone customer who wants a promised time is guided through the booking page.
- **The site emails website customers only**, twice: when the deposit is paid and when a technician is picked. The email sent before paying goes. Nothing is sent when a job is cancelled or moved. *(Changed 2026-11-08, Section 3dt: the technician email goes to a written-in job too, when it has an email address.)*
- **A technician is always picked by hand**, and on a website booking only once the deposit is paid.
- **Cancelling** takes a reason and has a "deposit refunded" tick. The 24-hour rule and the refund itself stay manual.
- **Finishing**: the admin types the final price, and how the rest was paid (card, cash, bank transfer). Every payment is a line on the job.
- **Notes** only the admin sees; a job can be **moved**; an enquiry gets **"Make this a job"**; a **history line** per change; **no job is ever thrown away**. Invoices come later, from the job's own data (built in Section 3dp).

### What was wrong

Thirteen faults, all found by reading the code or by driving the site, all fixed here:

1. **The email naming the technician could never be sent for a paid booking.** It hung off the admin's "Approve" button. A paid booking is already approved, by its payment, and the button showed only for an unpaid one.
2. **The admin's buttons answered nothing.** "Update Assignment" reloaded the page and looked the same whether it had saved or not.
3. **Buttons were offered where they made no sense.** "Complete" on a booking nobody had paid for; "Cancel" on one that was completed or abandoned, where it would have relabelled a finished job and put its hour back on sale.
4. **The payment badge was always green**, and read the database's own word ("DepositPaid", or "Cancelled" for a payment the customer had walked away from).
5. **The "Deposit Paid" row could not be read**: dark text on a dark card, from a style class that was never defined. It also showed the £50 when nothing had been paid.
6. **A cancelled or abandoned booking lost its date.** The time lived only on the slot it gave back; the list showed "Jan 01, 0001".
7. **The customer's confirmation page showed a two-hour window** for a one-hour slot.
8. **The same page promised a text message** from the technician. The business line is a landline over the internet and cannot send one.
9. **The reference was 36 characters in the emails and on the customer's page, and 8 in the admin panel.** A reference read out over the phone matched nothing on the admin's screen.
10. **Saved times were shown as the server keeps them**, in UTC: an hour early all summer, and the day before for a booking made just after midnight. The list converted them with the server's own clock, which is UTC on the servers.
11. **"Unblock" in the calendar did nothing.** It called the method that frees a slot from its booking, which leaves the block where it is. A blocked hour, or a day blocked with "Block Entire Day", could never be opened again.
12. **The calendar's buttons answered nothing either**, and "Release" put a paid booking's hour back on sale without a question.
13. **The list's "Pending Approval" card counted a step that did not exist**, and its other two figures left out cancelled bookings only by accident: they had no date. Once a cancelled job keeps its date it has to be left out by name.

### What was built

**Step 1, the website booking put right.**

Saved again as it stands, or cleared, no email goes. `AssignTechnicianAsync` returns what happened (`TechnicianAssignmentResult`) and the controller puts it into words.

- **One reference**, `BookingReference.Short`: the first eight characters in capitals, in both emails, on the customer's page, in the admin panel and on the Stripe payment line.
- **The customer's confirmation page** shows the slot's own hour and says an email with the technician's name follows.
- **`UkTime.FromUtc`** shows a saved moment as a UK clock does, on the job and enquiry pages. A machine that does not know the UK's time zone shows the time as saved, not an error page.

**Step 2, the two labels, and cancelling.**
- **`JobLabels`** turns the database's status names into the business's words (the job: Booked, Done, Cancelled, Abandoned) and works out the money label (Not paid, Deposit paid, Part paid, Paid in full, Deposit refunded). The list's filter offers the job labels.

**Around them.**

## 3cf. A Job's Details Can Be Put Right; Two Faults Fixed on the Way (2026-10-09)

## 3ci. The Database Server Closed to the Internet and Rebuilt; the Production Pipeline Written; a Deploy No Longer Signs the Admin Out; a UK Clock on the Servers (2026-10-09)

The first half of the production deploy (Launch Sprint L4 item 5). The live server has not been touched yet: this section is everything that could be made ready and checked without it. Reading for the plan turned up faults on the database server that had to be put right before any real booking is kept there, and those were dealt with first. `docs/WORKFLOW_DEPLOYMENT.md` has how both pipelines work now; this section records what changed and why.

### What was agreed (2026-10-09)

- **The plan was shown and agreed before anything was changed**: Cloudflare's origin certificate for the hop between Cloudflare and the server; the visitor's address worked out in the Caddyfile and not in the app; the UK clock as a server setting and not a code change; the live site with a deploy key, a database login, a photo bucket and GitHub secrets of its own; the image built again on `main`.
- **The work is done together, one step at a time.** The developer's instruction. Each change on the database server was said first and agreed before it was made.

### What was wrong

1. **The database answered from the internet.** The SQL container publishes port 1433 on every interface, and nothing stood in front of it. Section 1 of this file and the private notes both said the database could only be reached over the private network. It had been open since the server was made on 2026-07-08. The SQL log held just over a million failed sign-ins from 499 addresses, nearly all at `sa`, the first of them three minutes after the server started.
2. **The `sa` password was a weak one**, of the same pattern `AGENTS.md` already warns about. Known, and waiting to be rotated (Section 3w).
3. **The database files lived inside the container.** It had no volume, so removing or replacing the container, for an update say, would have taken both databases with it.
4. **SQL Server ran as Developer edition**, which Microsoft allows for development and testing and not for a live business.
5. **SQL Server had never made a backup.** Hetzner's automatic backups were on for all three servers from the start, which this file did not say; but those copy the disk while the database is running, and a database file caught in the middle of a write is not certain to open again.
6. **Both databases were on the FULL recovery model** with no log backups, which makes the log grow for ever once backups start.
7. **The compose file and the Caddyfile on a server were whatever somebody had last copied there by hand** (the trap of Section 3ae). On a live site a forgotten copy is an outage.
8. **Every deploy made new sign-in keys**, because they were kept inside the container: the admin was signed out, a form open at that moment came back "that didn't go through", and a password reset link already sent stopped working (Launch Sprint L4 item 5).
9. **The servers' clock is UTC**, an hour behind the UK all summer (Launch Sprint L4 item 16).
10. **A service picture uploaded in the admin panel is saved inside the container**, so the next deploy puts back the picture the build carries, or leaves a new service with none. Found, not fixed: Launch Sprint L4 item 19.

### What was done on the database server

- **A Hetzner Cloud Firewall in front of it**, letting in SSH and nothing else. Hetzner's firewalls do not filter the private network, so the web hosts reach the database as before. The failed sign-ins in the log stop at the minute it was applied.
- **Did anyone get in?** Nothing shows it: no login that should not be there, no changed server setting, nothing added to the system database, no server trigger or start-up procedure, the `sa` password last set on the day the server was made, and only the staging site connected. SQL Server does not log a successful sign-in, so that is not proof. What was there to read was staging's test data; `handyfix_prod` had no tables.
- **A new `sa` password**, 32 random characters, kept in the private notes and nowhere else. The site never used `sa`.
- **The container made again**, same build of SQL Server: its data on a Docker volume, Express edition. The old container is kept, stopped, until the new one has run for a while. Both databases were backed up from the old one with staging's database closed for writing, and restored into the new one; the staging site's login was made again with the same password. The system part of the new server is new, so nothing that might have been left behind in the old one came along.
- **SIMPLE recovery model** on both databases.
- **A nightly backup made by SQL Server itself**, 02:30 UTC, 14 nights kept, on the same disk so that Hetzner's copy carries it off the server. It signs in as a login of its own that may back up and nothing else; that login's password is in a file on the server that only root can read.

### What was built in the repository

- **`.github/workflows/deploy-prod.yml`**: runs on a push to `main`. One job builds, tests and pushes the image as `prod` and under its commit id; a second copies the two files and restarts the server. Only the second is given the server's key, from a GitHub environment named `production` that `main` alone may use.
- **`deploy/docker-compose.prod.yml`**: `Production`, port 443 only, no password prompt. A setting the site cannot run without is written `${NAME:?…}`, so a line missing from the server's `.env` stops the deploy with its name before a running container is touched.
- **`deploy/caddy/prod/Caddyfile`**: Cloudflare's origin certificate; Cloudflare's published address ranges as trusted proxies and `CF-Connecting-IP` as the header to believe from them; one address handed to the app in `X-Forwarded-For`; `www` redirected to the bare name; a request that arrives while a deploy is replacing the app's container made to wait for the new one.
- **`deploy/.env.prod.example`**: every setting the live server needs.
- **Both workflows copy their compose file and Caddyfile to the server at every deploy**, then ask Caddy to re-read its file. For that the Caddyfiles moved into folders of their own (`deploy/caddy/staging`, `deploy/caddy/prod`) and Caddy is given the folder: Docker mounts a single file by what it is on the disk at that moment, so a file replaced by a deploy stays invisible to a running Caddy.
- **`DataProtection:KeysPath`** (`Program.cs`): names a folder for the sign-in keys. Both compose files point it at a volume. Not set, nothing changes.
- **`TZ: Europe/London`** in both compose files.
- **The two SSH actions pinned to a commit** in both workflows. They are somebody else's code and are handed a server's key.
- **`AGENTS.md` Section 12** says what a merge into `main` means now.

### Decided on the way (2026-10-09, by the developer's agent; each is the business's to overrule)

## 3cs. The Job List's Filter No Longer Takes Seconds; the Calendar's Arrows Lead to the Nearest Day with Jobs (2026-10-23)

Two faults the developer found in the admin panel. The plan was shown and agreed before any code was written.

### The job list's filter

- **What the developer saw**: picking a filter on the job list took a long time to load the page.
- **What was measured locally**: a filter was slow only the first time it was picked, about 4 seconds, then about 0.2. Each sort column did the same. The time was spent inside SQL Server, planning one query (`Executed DbCommand (3,551ms)` the first time, 6ms the next). SQL Server keeps a plan for each query text it has seen, and each filter and each sort is a different text. It can lose a kept plan, after a restart for one, so the slowness came back.
- **Why the query was so heavy**: the job's row (`BookingDetailsViewModel`) checked its payments, services and photos for `null` before reading them. A list read from the database is never null, and SQL cannot ask it, so EF fetched each whole list to check it in C#. The query joined the payments three times over, the services twice more and the photos once more: ten joins where four do. They also multiplied the rows: a job with two payments and five photos came back as 200 rows, a figure that grows with every real job.
- **Proof before the fix**: the logged query was run in the local SQL Server as it was and with the six extra joins cut out. Planning took 2.6 to 2.9 seconds against 40ms.
- **The fix**: the five `!= null` checks are gone, with a comment saying why. The job's own page, the calendar's list of a day and the dashboard read the same row, so they are lighter too.
- **The same habit elsewhere**: `ServiceViewModel`, `ServiceDetailsViewModel` and `EnquiryViewModel` check a list for `null` the same way. Each loads one small list and those pages answered in under 40ms, so they were left as they are.
- **Not changed**: with a filter on, the page still reads the jobs twice, once for the table and once for the three cards over it, which describe the whole business. Each read costs a few milliseconds now.

### The calendar's arrows

- **What the developer saw**: the arrow did not light up when the next job was more than a day away.

With nothing that way it is grey and moves one day, as before, so the days can still be stepped through. Pointing at one says where it leads: "Next day with jobs: Mon 27 Oct", or "No jobs after this day. The day after: Sat 25 Oct".
- **Why the lit arrow jumps rather than moving a day**: lit but moving a day, it would open an empty day with the arrow still lit, and the admin would click through empty days. Jumping keeps Section 3ch's rule that a lit arrow never opens an empty list.
