## 3df. A Clean Build: No Warnings, and a Warning Now Fails the Release Build (2026-11-06)

The first of the Code Quality Sprints (Section 4, Q1). The build printed 283 warnings, most of them from three causes: C# files saved without a byte order mark, the generated migrations, and the two Identity page models (Login, Register) still in the template's style. A long list of warnings hides the one that matters, so the build is now at none, and the Release build stops on any new one. Nothing a customer or the admin sees changed.

### What changed

- **A byte order mark on 114 C# files** (StyleCop's SA1412), and `src/.editorconfig` tells editors to keep it. It sits in `src/` because the Docker image is built from that folder only.
- **Migrations read as generated code, and Razor page models free of the file-name rule**, both in `src/.editorconfig`. A migration is written by EF Core, and a page model named `LoginModel` can never match the file name `Login.cshtml.cs`.
- **Login and Register page models in the house style**, the way `ForgotPassword` and `ResetPassword` already were: usings inside the namespace, `this.`, members in order. Every message, redirect and step is as before.
- **The last StyleCop warnings** in services, controllers and tests: trailing commas and spaces, blank lines, members in order. Members were moved, never changed.
- **`KnownIPNetworks`** in place of `KnownNetworks`, which .NET 10 marks obsolete. The trusted proxy list is still emptied, as Section 3ac explains.
- **Service methods that nothing called, removed**: `RescheduleBookingAsync` (moving a job has been `MoveBookingAsync` since Section 3ce), `GetUserBookingsAsync`, `AddBookingImageAsync`, `GetAvailableSlotsForDateAsync`, `IReviewsService.GetPendingCountAsync`, `GetPaymentsForBookingAsync`, `GetAllPaymentsAsync` and `ICategoriesService.CreateAsync`, with the three tests that existed only for them. `CreateBookingAsync` lost a `userId` parameter its one caller never passed. Three methods that only their own class calls came off their interfaces and stay public for their tests.
- **The template's leftovers, removed**: the empty `HandyFix.Web.Infrastructure` project; the `Sandbox` console tool, an empty stub that migrated and seeded whatever database it was pointed at; the old `Settings.StyleCop` file, which the current analyzers never read and which disagreed with `stylecop.json`; the empty `site.min.js` and the bundle registered for it; five package versions only `Sandbox` used. The resolved packages of every remaining project are the same.
- **A warning fails the Release build** (`src/Directory.Build.props`). CI, the staging deploy and the live deploy all build Release, so code with a warning stops before it reaches a server, while a local Debug build still runs during an experiment. A report of a vulnerable package (NU1901 to NU1904) stays a warning, so that it cannot block an urgent deploy; it is fixed on purpose (AGENTS.md Section 8).
  - *The trade-off:* CI and the Docker image take the newest .NET 10 SDK (no `global.json` pins one), so a deploy that fails on a warning nobody wrote means a newer SDK brought a new warning. Nothing broken goes live that way; the warning is fixed and the deploy runs again.
- **Docs**: `docs/WORKFLOW_SERVICES.md` and `docs/WORKFLOW_DEPLOYMENT.md` no longer name what was removed or renamed, the README's project tree no longer lists `Sandbox`, and the older sections here that named a removed method say so.

### Verified

- **Build** 0 warnings, 0 errors, in Release and in Debug (was 283); **tests** 1008/1008 (384 + 624).
- **Each step read against the plan before it went on `dev`**; where a change was meant to be a pure move, a script compared each file's contents before and after.
- **A separate review of the whole sprint** found no change in behaviour: the Login and Register logic is the same statement by statement, clearing `KnownIPNetworks` was tried on the .NET 10 runtime and behaves as clearing `KnownNetworks` did, no view links the removed script, and nothing removed is named anywhere in the code, the solution, the Dockerfile or the workflows.

## 3dh. Faults the Code Audit Found, Put Right (2026-11-06)

The third of the Code Quality Sprints (Section 4, Q3): the four faults the audit of 6 November found, and two more found on the way. Unlike Q1 and Q2, these change what the site does, each exactly as written below.

### What changed

- **The booking form explains a booking it cannot take in our own words, and logs what went wrong.** `CreateBookingAsync` answers with a `BookingCreateResult`: created, slot taken, or slot not found. The form shows "This slot was just taken by someone else, please pick another." or "The selected time slot does not exist. Please choose a different time.", each with the slot cleared and the rest of the form kept. Anything else, such as a status missing from the database or the database out of reach, is logged and shows "An error occurred while saving your booking. Please try again." Before, the text of any `InvalidOperationException` went to the customer as it was, including an internal "Booking status 'Pending' is not seeded.", and two of the failure paths logged nothing.
- **A booking and its photos are saved together.** The photo rows used to be saved after the booking's transaction was committed. A photo save that failed told the customer to try again while the booking kept its hour, and the retry found the hour taken by their own booking. They are in the booking's own save now: all of it or nothing.
- **A job is not cancelled when its deposit is paid in the same moment.** When the admin cancels a booking still waiting for its deposit, its Stripe payment page is closed first. If Stripe answers that the page was paid just then, the booking is already confirmed and both deposit emails have gone; the cancel used to go on regardless, telling the admin the customer had not been emailed. Now nothing is changed, and the admin reads "Nothing was changed: the customer paid the deposit just now, so the booking is confirmed and they have been emailed. Cancel it again if it still has to be cancelled." When Stripe cannot be reached, the job is cancelled as before (Section 3cg).
- **Delete and remove buttons always ask first.** Seven admin buttons (delete a technician, a service area, a service, a review or an enquiry; take a payment off a job; put a calendar hour back on sale) asked through an inline script that held the name. A name with an apostrophe, such as O'Brien, ended the script's string: the script failed and the form was sent without asking. The question now sits in a `data-confirm` attribute, which the browser reads as plain text, and one listener in `site.js` asks it. Each question reads as before.
- **The admin's picture errors in our own words.** Under the picture box of a service's Create and Edit pages, any exception's own text used to show, the storage library's and the picture library's included. The two messages written for the admin ("Unsupported file type. Only JPEG, PNG, and WEBP images are allowed." and "Failed to decode uploaded image.") still show; anything else is logged and reads "The picture could not be saved. The service itself is saved: try the picture again."
- **Found on the way: a new service whose picture fails opens on its Edit page.** A service is saved before its picture. The Create form used to come back with the error, and sent again it only said the name was taken. The admin now lands on the new service's Edit page with the reason under the picture box; a refused file reads "The service is saved, but not its picture." followed by the reason. The developer's decision.
- **Found on the way: an area's nearby areas in the same order on every visit.** They were ordered by drive time alone, so two areas the same drive away could swap places between visits, and search engines saw the page change. A tie now goes by display order, then by name. The developer's decision.
- **Docs**: `docs/WORKFLOW_BOOKINGS.md` and `docs/WORKFLOW_SERVICES.md` describe the new behaviour; Section 5 here now records that an answer a page has to react to is a result, not an exception; the older lines that named the removed `SlotUnavailableException` say what became of it.

### Verified

- **Build** 0 warnings, 0 errors (Release); **tests** 1032/1032 (394 + 638), with a test for each outcome and each message. Sqlite tests prove that a failing photo save, and a slot taken in the same moment, leave no booking, no photo and the hour as it was; the Stripe tests prove that a page paid at the moment of cancelling leaves the booking confirmed with no cancel line in its history, and that Stripe out of reach still cancels.

- **A separate review of the whole sprint** found nothing changed beyond the list above. The booking, its photos and the slot are written through one database context inside one transaction; the cancel has one caller; both layouts load `site.js`, and no public form carries a `data-confirm`, so the person check on the public forms is untouched.
- **Staging, after the push** (pipeline green in about two minutes), in the admin panel: a technician "Test O'Brien" got the dialog with his name, Cancel kept him and OK deleted him; a job written in and then cancelled read "The job is cancelled…" and Cancelled; a new service with a text file as its picture landed on its Edit page with the line under the picture box, and was deleted after. ## 3di. Emails and the Admin's Job Actions in Classes of Their Own (2026-11-06)

The fourth of the Code Quality Sprints (Section 4, Q4). A refactor: nothing a customer or the admin sees or is sent changed, word for word.

### What changed

- **Each kind of email has a class of its own**, in `src/Services/HandyFix.Services.Data/Emails/`: `BookingEmails` (the deposit confirmation to the customer, the deposit notice to the company, the notice of a deposit for a booking not held, the technician's name to the customer), `EnquiryEmails` (the notice of an enquiry or an application to the company, the acknowledgement to the sender) and `AccountEmails` (the password reset link). Each holds every word of its emails and answers whether the email went. The service that sends one still decides when, and still writes the history line and the `EmailsNotSent` row when it did not go, in the same save as before. This reverses Section 3cl's "each email's words stay in the service that sends it", by the developer's decision: `BookingsService` and `PaymentsService` had grown too long to read, with the emails' HTML in the middle of the booking logic.
- **The email helpers moved with them**: `EmailLayout`, `EmailText`, `EmailSettings`, `EmailColour` and `EmailSenderExtensions`, from `Common/` to `Emails/`. `JobHistory` and `SlugGenerator` stay in `Common/`.
- **The admin's actions on a job are in `JobsService`**: write a job in, complete it, change its final price, pick its technician, cancel, move, put its details right, its notes and its history. `BookingsService` keeps the website's side of a booking (making it, dropping it when its deposit never comes) and the lists, the calendar and the counts. The method bodies moved unchanged. `PaymentsService` stays whole: it owns the payment rows and their statuses, and taking the admin's money actions out of it would spread those rules over two classes.
- **Fewer dependencies each**: `BookingsService` no longer takes the email sender, the settings, the logger, or the technician and booking-service repositories; `PaymentsService`, `InquiriesService` and `AdminAccountService` no longer take the email sender.
- **Tests**: `TestEmails` builds the real email classes around a test's mocked sender, so every test of an email's words still reads them; the admin controller's tests mock `IJobsService` for the actions.
- **Docs**: `docs/WORKFLOW_EMAIL.md` says where each email's words are now, and `docs/WORKFLOW_BOOKINGS.md` names `JobsService` for the admin's actions; Section 5 records the new rule.

## 3dj. Page Scripts in Their Own Files, and Logic Out of the Views (2026-11-06)

The fifth of the Code Quality Sprints (Section 4, Q5). A view now draws its page from what its controller and model hand it: the scripts are files the browser keeps between pages, and the sums, labels and file lookups are worked out before the page is drawn, where they can be tested. Nothing a customer or the admin sees changed; three small faults were put right on the way, each named below.

### What changed

- **The booking page's script is `wwwroot/js/booking.js`**, 468 lines that were inline. What it needs from the server is on the form as `data-` attributes, which Razor encodes: the districts served, the service and the day from the link, the slot kept when a form comes back, the deposit and the description's minimum. The minimum is one constant, `BookingInputModel.ProblemDescriptionMinLength`, used by the server's rule and the page. *Fix:* "today" in the calendar is the visitor's own date; the script took the date in UTC, which between midnight and 1am in summer opened the calendar on the day before. The list of available dates the controller fetched for the page and the page never used is gone, with `GetAvailableDatesAsync` and its tests.
- **The other page scripts are files too**: the confetti on Booking Confirmed, "Try again" on the payment page, the home page's fade-in, one accordion for the FAQ and the Pricing questions (the FAQ still opens on its first, Pricing on none), one search for the five admin lists, and in `site.js` the cookie banner's Accept and the service page's picture fallback. Inline `onclick` and `onchange` handlers are `data-` attributes that `site.js` reads. Three things stay inline on purpose: the form guard's few lines, which must run while the page is read, the image `onerror` fallbacks, which must be there before the picture loads, and the JSON-LD data for search engines. A test keeps every public page, and the booking and admin pages, that way.
- **The job pages' labels and money lines**: `StatusBadges` gives each job and money label its colour, where the job's page, the job list and the calendar each had the same ternary. The job's view model works out whether a job can still owe money, its two "still owed" lines, whether its time was promised and why no technician can be picked, with tests for each state. The calendar looks up the jobs at an hour once, instead of searching the day's jobs for every slot.
- **One helper each** for the admin lists' sort links (`ISortableList` and one `NextDescending`, where three pages had a copy), the category icons (`CategoryIcons.ForSlug`, matched on the slug instead of the name) and a service's duration (`Durations.HoursOrMinutes`). The home page's "45m" and the admin's "45 mins" print differently on purpose and stay.
- **Page data in the model**: the Contact form's categories are `ContactInputModel.Categories`, and the admin technician and area forms ask their model whether they add or update (`IsNew`), where both came in `ViewData`. `BaseController.SetPageMeta` sets a page's title, description and address in one call. *Fix:* the Contact, Booking and Join forms shown again after an error keep the page's description and address, which they lost. *Fix:* `/Services` has a description for search engines; it had none. The Contact controller's title is gone: the view's "Get a Custom Quote" always replaced it.
- **Files looked up before the page is drawn**: the home page's card pictures' smaller copies (it looked each one up twice while it was drawn), the category page's and the pricing cards' copies, an area page's phone picture and the admin area page's "picture in place" are found by the controllers (`PictureLookups`). No public or admin view injects the picture storage or the web host environment any more.

### Verified

## 3ef. A Service a Job Has Is Not Deleted (2026-11-11)

- **`ServicesService.DeleteAsync` returns whether it deleted**, and deletes nothing for a service that a job has. ## 3fa. The Site Counts What Its Visitors Do (2026-11-14)

Item 8 of the SEO plan, the last one. The site uses no analytics service, so nothing told "nobody comes" from "they come and do not book", and a tap on Call or WhatsApp, which is how many customers of a trade get in touch, left no trace at all. The site now counts those things itself and shows them on the admin Dashboard.

- **What is counted.** A visit (on a phone or on a computer), the booking page opened, a free time picked, Call tapped and WhatsApp tapped. The Dashboard puts beside them the bookings made on the website, the deposits paid and the enquiries sent, which it reads from the panel's own records.
- **Sums only.** A `SiteCount` row is a day, a kind and a number, and its key is the day and the kind, so there is one row of each. It holds no address, no browser and nothing that tells one visitor from another, which is why it is not built on the base model with its dates. `SiteCountsService.AddAsync` adds one in a single statement the database itself runs ("Count = Count + 1"): a read followed by a write would lose one of two counts made in the same moment. The day's first of a kind makes the row; if two visitors make it at once, the key refuses the second, which is then added to the first.
- **What a visit is.** A page reached from outside the site (a search, a link, the address typed in), counted once the visitor scrolls, taps, presses a key or moves the mouse: a program that reads pages does none of those. The pages a visitor goes on to are the same visit, and so are a page shown again by Reload or Back and the return from the payment page. It is a count of visits and not of different people: the same person coming in the morning and in the evening is two. Telling people apart needs a cookie or a code made from the visitor's address, and the site keeps neither.
- **Nothing in the visitor's browser.** The script (`site.js`) writes nothing there and reads nothing kept there, and what it sends is one of five words, once for each page shown. Call and WhatsApp are known by where their links go (`tel:` and `wa.me`), so every such link on every page is counted with nothing added to the views.
- **Whose browser is counted** is decided in `SiteCounting`: not a program that reads pages, by what it calls itself (search engines, link previews, speed tests, a browser driven by a script, this project's own checks among them); not the admin signed in; not a browser the admin panel has marked; and not a request sent by a page of another site.
- **The business's own browsers.** `AdministrationController` marks a browser the first time it opens the admin panel, with a cookie that only the business's own browsers ever get. From then on that browser's looks at the public site are left out of the figures, signed in or not. A button under the Dashboard's table puts the browser back into the count, to try the count out, or takes it out again.
- **The address.** `POST /count` (`CountController`) takes no antiforgery token: the token is written into a form and most pages have none, and the request does nothing as anybody. It has a rate limit of its own (`RateLimits.CountsPolicy`), answers the same whatever came in, and never shows an error: nothing there is the visitor's to see or to put right.
- **The Dashboard.** "What Visitors Did on the Website" has eight rows, for the last 30 days or since the count began. The bookings, deposits and enquiries are counted from the day the count began, so that the rows can be read against each other. Quick Actions moved above the two tables, and each table keeps its own period when the other's is changed.
- **Left out on purpose:** where a visitor came from and which page they arrived on. Search Console and the Google profile's own figures already say how many people come from Google and to which pages; what nothing else could say is what they do once they are on the site.
